# Task 10-I — Shape-First 추가 최적화

2026-11-03. 직전 GPU sampling/output 경로를 기준으로 외곽선 정규화,
연결 성분 반복과 FPS 경계 계산의 중복을 줄였다. 선택 정책·점 수와 GPU 출력
규약은 유지했다. 로봇 필터는 수정하지 않았다.

## 결과

VastAI **58752018**, AMD EPYC7543, RTX3090. 기존 Python3.12.15,
Torch2.14.1+cu130, Triton3.8.0, NumPy2.5.4 환경을 사용했다.
앞선 작업과 같은 실제 hand-camera **512×512** 입력이다. Peg61,056 pixels,
Box0 pixels이며 선택점은1,105개다.

측정은 compact CUDA 좌표·특징 준비 완료 → 전체 sampling 출력의 GPU 계산
완료까지다. 양 끝에서 CUDA를 동기화한다. 역투영·PCA/특징, IO, 검증용
다운로드, 로봇 필터/gate, packet·최종 Graph 조립은 제외한다.

Warmup20회 후 before/after를 번갈아100회씩 실행한 최종 결과:

| 경로 | 중앙값 | p95 |
| --- | ---: | ---: |
| 직전 최적화 경로 | **8.333ms** | **8.642ms** |
| 이번 추가 최적화 | **7.714ms** | **7.967ms** |

동일 실행 기준 **7.43% 추가 감소**, 약1.08배다. 과거8.920ms와 이번7.714ms를

변동했다. CPU affinity·공유 host 부하는 고정하지 않았다.

모든 기본/diagnostic 후보·대표점·선택점·특징·validity·출처 배열이 이전 경로와
`rtol=0, atol=0, equal_nan=True`로 일치하며 CUDA에 유지된다. `device='cpu'`
명시적 반환도 보존한다. 한 입력의 수치를 새 데이터셋이나 모든 mask의 고정
향상률로 해석하지 않는다.

## 적용한 변경

### 외곽선 canonical walk

기존 kernel은 초기 walk를 자기 자신과 끝까지 비교했다. 이 비교는 결과를
개선할 수 없으므로 생략했다. 최소 source의 재방문 위치 검색과 최종 복사는
256-element tile로 병렬화했다. 양 방향과 반복 최소점의 lexicographic 선택은
유지한다. 얇은 구조에서 양 방향이 완전히 같으면 필요한 비교는 그대로 한다.

실제 호출에 사용된 CUDA walk/offset/length를 잡아 그 kernel만 별도로 재실행한
최종 표본은 **0.317ms →0.023ms**였다. 이 값은 전체 frame의 가산 가능한
시간 예산이 아니라 독립적인 kernel 진단이다.

### 연결 성분 압축·종료 확인

기존에는 매 round마다 compress → parent copy → flag clear → union을 각각
호출하고 CPU가 flag를 읽었다. Compress kernel에서:

- 계산한 root를 root 배열과 parent 배열에 함께 기록한다.
- 다음 union의 changed flag도 초기화한다.
- Union 두 round를 완료한 뒤 CPU가 수렴을 확인한다.

Compress 도중에는 union이 실행되지 않으며 각 parent store는 같은 component의
안정된 root로 기존 경로를 단축한다. 다른 thread가 이전 경로나 단축된 경로를
읽어도 root는 같다. Flag clear는 union보다 앞선 kernel 안에서 끝나므로 별도
clear와 경쟁하지 않는다. 종료 flag가 false가 될 때까지 실행하며, 정해진 적은
round 수로 근사 종료하지 않는다. 보호용 상한을 넘으면 오류를 낸다.

Canonical/연결 성분 변경만 적용한 paired 중간 결과는8.919→8.501ms였다.

### FPS seed-tile 경계 공유

직전 pruning kernel은 모든 point block이 같은 seed tile의 XYZ min/max를
반복 계산했다. 새 구현은 현재 구조점의 tile 경계6개 값을 **tile당 한 번**
구한 뒤 모든 point block이 공유한다. Seed XYZ는 실제 거리를 계산해야 할
때만 읽는다. Bucket padding처럼 활성 점이 전혀 없는 block은 seed scan을
건너뛴다.

경계 buffer는 FPS plan에 보존하되 **현재 XYZ/구조점으로 매 호출 재계산**한다.
관측이나 이전 frame의 선택 결과를 재사용하지 않는다. 경계는 입력 XYZ dtype으로
저장하고 FP64로 읽어 거리 하한과 거리 계산을 수행한다. Min/max는 원래 입력
좌표값이므로 FP32 XYZ의 min/max를 FP32로 저장해도 값은 달라지지 않는다.

CUDA Graph에 경계 생성 kernel 하나가 추가되지만 반복 경계 계산과 불필요한
seed 좌표 load가 줄어든다. 작은 eager FPS 호출은 직전 경로를 유지했다.
이번 변경은 거리쌍 자체를 더 줄인 것이 아니라 같은 경계의 중복 계산을 줄인
것이다. 거리 기준·FP64 연산·first-source 동점 처리·surface97/95는 유지한다.

## 최종 구간 진단

각 함수의 입력을 준비한 뒤 따로 실행·동기화한30회 중앙값이다.

| 구간 | 기준 | 추가 최적화 |
| --- | ---: | ---: |
| 외곽선 전체 | 2.080ms | 1.711ms |
| Canonical kernel 단독 | 0.317ms | 0.023ms |
| FPS 전체 | 3.362ms | 2.742ms |
| Voxel PCA | 0.668ms | 0.668ms |
| Voxel silhouette | 0.750ms | 0.751ms |

구간을 따로 호출하면 CPU enqueue와 GPU 실행의 겹침, clock·allocation 상태가
전체 실행과 달라진다. 특히 canonical 단독 표본은 이미 할당된 buffer로 kernel만
재실행한다. 구간 값들을 더하거나 두 구간의 차이를 더해 전체 감소량을 만들면
안 된다. 최종 주장은 같은 process의 전체 sampling paired 표본을 기준으로 한다.

## 초기 비용·남은 범위

최종 process의 첫 함수 호출은 기준224.012ms, 최적화270.832ms였다.
디스크 JIT cache는 앞선 실행으로 형성된 상태이며, JIT loading/초기화와 graph
생성 등을 함께 포함한다. **7.714ms는 warm 성능**이다. 새 capacity/stream의
plan 생성 비용과 per-frame 성능을 구분해야 한다.

외곽선은 여전히 scalar bounds 반환, 동적 `nonzero`/allocation과 CPU 수렴 확인을
사용한다. 확인 횟수를 묶었으며 완전한 device-only 종료 처리는 아니다.
Full sampling의 완전한 CUDA Graph capture도 아니다. 이후 비용이 큰 구간은
여전히 FPS와 외곽선이며, workspace 재사용·데이터 배치 같은 추가 후보는 남아 있다.
최종 NumPy Graph 소비자의 명시적 CPU 반환은 이 작업 범위 밖이다.
