# Task 10-I — 물체별 최종128점 FPS를 GPU로 전환

2026-11-03. 기본 triton_fused 경로의 최종 일반 FPS를 GPU로 옮겼다.
같은512 입력·EE 기준 paired 중앙값은 **CPU3.951ms → GPU1.240ms**, 약3.19배다.
GPU FPS 후 다음 Graph용 CPU 기록 반환까지 포함하면2.459ms다.
선택점·순서·특징·병합 출처와 최종 Graph tensor는 기존과 정확히 일치했다.

## 구현·기본 연결

- [Tensor API](../../graph/persistent_geometry/tensor_records.py)의
  `budget_tensor(records,count=128)`가 nonnegative integer cap을 물체별로 적용한다.
  입력 TensorRecords의 명시적 CPU/CUDA device에 결과를 유지한다.
- [Triton kernel](../../graph/persistent_geometry/tensor_records_kernels.py)이
  float64 FPS의 전체 반복을 하나의 device loop에서 수행한다.
- [CurrentGeometry](../../graph/plan_a_bc/geometry.py)에서
  GPU3mm dedup 결과에 직접 적용하고, CPU `budget`를 호출하지 않는다.
- `final_fps_backend='torch_cuda'` metadata로 실제 기본 경로를 확인할 수 있다.

```text
GPU view check → GPU records → GPU3mm dedup
  → budget_tensor(...,128)                         GPU 결과 반환
  → numpy_records                                 명시적 호환 반환
  → 기존 CPU Graph 구성·엣지 생성                  후속 소비자
```

최종 FPS 직전의 CPU 반환을 없애고, 반환 경계를 FPS 이후로 옮겼다.
이 단계 결과와 모든 특징·출처 배열은 GPU에 있다. 기본 최종 Graph 생성/반환까지
전부 GPU로 이식한 것은 아니다. `numpy_records`는 그 Graph 소비자를 위한 명시적
변환이다. 기존 CPU perception과 별도 `cuda_resident` prototype의 native CPU 경로,
로봇 필터/gate는 수정하지 않았다. 학습/평가·정책 성공률도 측정하지 않았다.

## 기존 선택 규칙 유지

기존 일반 `budget(records,128)`의 `hybrid=False` 동작을 따른다.

1. 물체별 입력이128점 이하면 **입력 순서 그대로** 반환한다. 부족한 점을 보충하지
   않고, empty 물체는 empty로 유지한다. Structural anchor를 별도로 고정하지 않는다.
2. 더 많으면 기존 persistent ID **문자열 순서**의 첫 점으로 시작한다.
   동률 역시 같은 문자열 순서와 stable input order를 따른다.
   예를 들어 같은 camera에서 pixel10의 문자열은 pixel2보다 먼저다.
3. 거리 계산은 float64의 `(dx²+dy²)+dz²`이며 FP contraction을 끈다.
   이미 고른 점은 거리-1로 제외하고, 가장 가까운 선택점까지의 거리가 가장 먼
   다음 점을 고른다. 첫 점 이후127회 선택을 host 반복 없이 처리한다.
4. 선택된 row에서 XYZ/normal/F5/validity/object/structural을 그대로 gather한다.
   Ragged source offsets를 다시 구성해 선택한 representative의 **모든 병합 출처를
   같은 순서로** 보존한다. 평균하거나 다른 점의 특징을 붙이지 않는다.

문자열 정렬을 위해 camera prefix와 decimal int64 pixel을 GPU에서 UTF-8 byte key로
만든다. 양수 int64 seven-byte limbs를 stable lex sort하므로 prefix camera 이름,
Unicode, 전체 nonnegative int64 pixel 범위도 보존한다. Episode/time은 공통 metadata다.
실제 point ID를 CPU 문자열 배열로 내려서 정렬하지 않는다. 작은 정적 camera 이름과
10의 거듭제곱 표만 device별 최대8개 cache로 재사용하며 실제 point/pose를 cache하지 않는다.

물체별 oversized cloud에 FPS kernel 한 번을 호출한다. 작은 cloud는 register에서
최소 거리를 유지하고, 큰 cloud는 bounded chunk와 O(N) scratch를 사용한다.
N×N 거리 행렬은 만들지 않는다. Dynamic object/source compaction과 aggregate 입력
검사에는 scalar/shape 동기화가 남는다. Zero-sync 또는 순수 kernel 시간이라는 뜻은 아니다.

## 측정 조건·endpoint

VastAI **58752018**, RTX3090, AMD EPYC7543의 기존 환경을 사용했다.
NumPy2.5.4, Torch2.14.1+cu130. OMP/BLAS/MKL/Torch threads1,
CPU affinity·공유 host 부하는 고정하지 않았고 기본 Python GC를 유지했다.

동일한 실제 `10i_s1_0844_t080` hand512×512 입력이며, dedup 후 **Peg212→128점,
Box0점**이다. Base는 hand depth/calibration을 복제한 빈 관측이다.
**독립적인 두 실제 camera나 nonempty Box의 FPS 성능 측정은 아니다.**
두 물체와 여러 camera가 모두 있는 경우는 합성 계약 테스트로 검증했다.

앞선 baseline에 저장한 XYZ/persistent ID/선택 row NPZ와 이번 입력·선택 순서가
정확히 같은지 검사했다. 상류 packet/view/dedup과 CPU 준비는 timer 밖이다.
각 frame/mode20회 warmup 후100회 측정했다. Mode/frame 순서를 회전·역순으로
교대했고, 이전 출력 해제·logger·file IO는 다음 timer 밖이다.
CUDA 시작 전 대기는 timer 밖, 반환 후 완료 동기화는 timer 안이다.
JIT와 정적 identity cache는 warm 상태다. 아래 값은 CPU wall `perf_counter`이며
Python 제어·검사·정렬·할당·출처 gather와 GPU 완료를 포함한다.

| Mode | 시작 → 종료 |
| --- | --- |
| `cpu` | 준비된 CPU212점 기록 → 기존 NumPy128점 FPS 결과 |
| `gpu` | 준비된 GPU212점 기록 → 문자열 순서/FPS/특징·출처 gather → GPU 결과 |
| `gpu_to_cpu` | 위 GPU 단계 + 실제 post-FPS CPU 기록 반환 |
| `legacy_from_gpu` | 같은 GPU212점 기록 → 기존 CPU 기록 반환 → 기존 CPU FPS |

## 결과

| 좌표계 | Mode | 중앙값 | p95 |
| --- | --- | ---: | ---: |
| EE, 기본 | 기존 CPU `cpu` | 3.951035ms | 4.216698ms |
| EE, 기본 | **GPU 출력 `gpu`** | **1.239970ms** | **1.334753ms** |
| EE, 기본 | GPU + CPU Graph용 반환 `gpu_to_cpu` | 2.459371ms | 2.709862ms |
| EE, 기본 | 기존 readback + CPU FPS `legacy_from_gpu` | 5.858301ms | 6.660452ms |
| World | 기존 CPU `cpu` | 3.887290ms | 4.626564ms |
| World | **GPU 출력 `gpu`** | **1.202585ms** | **1.345874ms** |
| World | GPU + CPU Graph용 반환 `gpu_to_cpu` | 2.358950ms | 2.564230ms |
| World | 기존 readback + CPU FPS `legacy_from_gpu` | 5.709805ms | 6.014102ms |

EE resident 비교는 약3.19배, 동일 GPU 입력·CPU 출력 조건은 약2.38배다.
앞선 CPU baseline3.952ms는 이번 CPU3.951ms와 같은 endpoint다.
두 resident 행은 각각 해당 device에 입력이 이미 있다. 실제 후속 CPU 소비자까지
동일한 시작/종료 경계의 개선은 `legacy_from_gpu`와 `gpu_to_cpu`로 비교한다.
중앙값 차이를 순수 D2H 시간으로 해석하지 않는다. 호환 반환에는 Python 기록·배열
구성도 포함되며 새 경로는212개 대신128개 representative와 그595개 source를 반환한다.
선택에서 제외된 representative의 source를 보존한다고 주장하지 않는다.

Raw 표본은 제거하지 않았다. EE CPU 최대16.572ms 등의 지연도 보존했다.
원인을 따로 계측하지 않았으므로 GC/host scheduling 중 하나로 단정하지 않는다.
동일 입력의 반복 결과이며 전체 pipeline·다양한 장면의 지연 분포는 아니다.

## 검증

- Vast에서 관련 **64개 테스트 전부 통과**. CUDA FPS/키 생성/출처 gather를 실제로
  실행했다. macOS는64개 중40개 통과·24개 CUDA skip이며 CUDA는 실행하지 않았다.
- 빈/짧은/정확히128점/초과 입력, 두 물체, World/EE, permutation, coincident points,
  string-vs-numeric seed, stable tie, 2,301점 chunk, near ties를 검사했다.
- Prefix/Unicode camera와 `0..2**63-1` source pixel의 실제 문자열 정렬 일치를 검사했다.
- 기존 dedup에서 병합된 모든 출처의 순서,0 cap, 입력 불변성, 잘못된 count/frame/XYZ도
  검사했다. GPU FPS에서 `.cpu()`, `.numpy()`, `.tolist()`를 금지해도 통과했다.
- 기본 Graph test는 CPU final `budget` 호출을 금지해도 통과하며 GPU backend metadata를
  확인한다. 기존 CPU view/records/dedup과 observation readback 금지 검사도 유지했다.
- 실제512 입력에서 기존 CPU 선택과 **모든 기록 field/dtype/value/순서/출처가 정확히
  일치**했다. 두 frame 모두 선택128개, 그 그룹의595개 source가 동일했다.
- 실제 FK/public `CurrentGeometry`를 frozen pre-port class와 비교했다. 두 frame 모두
  **131nodes/1,006edges**, records·출처와 `node_input/node_type/edge_index/edge_attr/edge_type`
  전부 정확히 일치했고 모든 최대 절대 차이는0이다. 이 Graph 구성은 timer 밖이다.
- 비교는 준비된 mask/gate와 `robot_filter_backend='cpu'`의 prepare 대체를 사용해 로봇
  필터를 실행하지 않았다. 이번 결과를 로봇 필터·gate의 새 검증이라고 해석하지 않는다.
