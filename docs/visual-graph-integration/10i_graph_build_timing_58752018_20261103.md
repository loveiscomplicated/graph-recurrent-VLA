# Task 10-I — 기존 엣지 생성·최종 Graph 구성 시간

2026-11-03. 현재 기본 triton_fused 경로의 후속 CPU Graph를 그대로 측정했다.
최종128점과 CPU 기록이 준비된 시점부터 Graph 구성·최종 검증·반환까지,
**EE 중앙값792.852ms, p95 819.174ms**였다. 이번 입력에서는 표면 엣지의
free-space 검사와 그 안의 반복적인 전체 깊이 배열 생성이 큰 비용이다.
런타임 구현·엣지 규칙은 변경하지 않았다.

## 측정 endpoint

`PlanA.graph(records,data,cameras)`와 `CurrentGeometry._finish(...)`를 기존대로 호출한다.
시작할 때 CPU의 최종128점 기록, robot geometry, calibration, raw signed-mm depth가
준비되어 있다. 종료는 `(graph,records,gate)` 반환이다.

- 입력/frame 검사와 stable ID 순서의 노드 재배치. Point cap은 이미 적용되어 있으므로
  여기서 `point_cap=None`이다. 반복 최종 FPS를 다시 실행하지 않는다.
- 로봇 좌표, 노드 XYZ/F5/availability/validity와 zero temporal extras 구성.
- 표면 내부 엣지의 KD-tree neighbors, normal/tangency, 중간 표면 witness,
  camera depth 기반 free-space 검사.
- 로봇–물체 k4, Peg–Box M16 후보 연결, 양방향화·타입·edge attributes 구성.
- CPU Torch tensor wrapping, schema/status metadata, 출처·현재 시점·최종 Graph 검사.

GPU→CPU 반환, 앞선 projection/PCA/Shape-First/view/records/dedup/최종 FPS,
robot FK·필터·gate는 제외한다. 로봇–물체 **엣지**는 대상에 포함한다.
Model packing/device upload/encoder/inference도 제외한다. 반환 Graph는 CPU다.

이번 대상은 default `triton_fused`의 `PlanA.graph`가 직접 호출하는
`graph.persistent_geometry.graph`의 NumPy/SciPy 구현이다.
별도 `cuda_resident`/`SmallGraphConsumers`/native edge context는 사용하지 않았다.
과거 다른 구현·입력·endpoint에서 나온 수ms 수치를 이번 기준으로 재사용하지 않는다.

## 입력·실행 조건

VastAI **58752018**, AMD EPYC7543, Python3.12.15, NumPy2.5.4,
Torch2.14.1+cu130. GPU 준비는 RTX3090에서 실행했고 계측 대상은 CPU다.
OMP/BLAS/MKL/Torch threads1, CPU affinity·공유 host 부하는 고정하지 않았다.
기본 Python GC를 유지했다.

앞선 작업과 같은 실제 `10i_s1_0844_t080` hand512×512 표본이다.
**Peg128점, Box0점**, robot3개와 합쳐131nodes다. Base는 hand depth/calibration을
복제한 빈 mask/관측이다. Graph free-space 검사는 두 camera 객체의 깊이를 모두
확인하므로 빈 base라도 depth 검사 비용은 존재한다. 서로 다른 두 실제 sensor나
nonempty Box의 성능 측정은 아니다.

현재 실제 GPU pipeline으로 records/dedup/FPS를 실행하고 `numpy_records`까지
timer 밖에서 끝냈다. 실제 FK/public `CurrentGeometry.build`의 반환과도 비교했다.
`robot_filter_backend='cpu'`와 준비된 조건으로 `system.prepare`를 대체해 로봇 필터와
gate를 실행하지 않았다. 해당 알고리즘의 새 검증이나 변경을 수행한 것은 아니다.

## 별도 내부 진단

기본 측정 이후 각 frame5회 warmup·20회 별도 실행했다.
기존 호출을 감싸 시간을 재고 원래 `CameraObservation.depth` getter도 그대로
실행했다. Cache나 shortcut은 추가하지 않았다. 이 실행은 계측 오버헤드와 별도 실행
변동을 포함하므로 위 기본 합계에 직접 대입하거나 합산할 수 없다.
특히 표면 엣지 → free-space → depth getter는 **서로 포함된 부모·자식 구간**이다.

nearest 계산 자체이며 나머지 배열/타입·양방향화 비용은 기타 구성에 포함된다.

## 반복적인 depth 생성 확인

두 frame의 모든20개 진단 표본에서 호출 횟수는 동일했다.

- 표면 엣지 후보584개, normal 검사에서40개, witness 검사에서53개 제외.
- 남은 **491개 pair**에서 free-space 검사를 호출했다. Free-space rejection은0개다.
- 각 pair는 두 camera를 확인하고, camera마다 `camera.depth.shape`와
  `camera.depth[v,u]`를 각각 호출한다: **491 ×2 ×2 =1,964회**.
- 이 getter는 접근할 때마다 raw int16 depth를 float64 metre로 변환하고 invalid를
  NaN으로 배치한다. 512×512 전체 배열을 매번 생성한다. Cache가 아니다.
- 즉 Graph1회에 약5.15억 pixel회 규모의 전체 depth 변환을 수행한다. 선택된
  표면 witness의 소수 pixel을 조회하는 동작이 반복적인 전체 이미지 작업을 유발한다.

호출 횟수와 getter 합계는 실제로 계측했다. 이 입력에서 후속 최적화가 확인해야 할
명확한 대상이다. Getter 시간을 제거했을 때의 개선폭을 이미 측정했다고 주장하지 않는다.

## 정확성·실행 확인

- 입력128개 기록과 source provenance가 공개 `CurrentGeometry.build`와 정확히 일치했다.
- 기본·진단 실행 모두 다섯 Graph tensor와 packet metadata가 정확히 일치했다.
- 두 frame 모두 **131nodes /1,006 directed edges**: 표면982, 로봇–물체24, Peg–Box0.
- 입력 기록·robot data의 불변성, CPU output device를 확인했다.
- 전체 Graph tensor와 packet을 보존해 후속 구현의 동등성 비교에 사용할 수 있다.
- 로컬은 구문/import/CLI를 확인했다. Vast에서 실제 상류 CUDA 준비와 현재 CPU Graph
  실행·출력 비교·계측을 완료했다. macOS CUDA와 GPU Graph 구현은 실행하지 않았다.
- 이번 작업은 기준 측정뿐이다. Runtime과 simulator·로봇 필터·학습 코드는 수정하지 않았다.
