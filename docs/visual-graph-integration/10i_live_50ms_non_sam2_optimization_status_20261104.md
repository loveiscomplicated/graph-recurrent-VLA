# Task10-I 주 live 50ms 목표와 SAM2 외 최적화 현황

정리 기준: **2026-11-04 KST**. 기존 실측과 목표를 정리한 뒤, 사용자 요청으로
GPU 전환 직전 CPU·NumPy 구현의 **동일 입력 비교 측정**을 추가했다.
아래 표에 CPU 열을 추가하고 GPU 열도 같은 관측의 재측정값으로 갱신했다.
[추가 비교 원문·경계·원자료](10i_live_preopt_cpu_comparison_58752018_20261104.md)를 함께 읽는다.
Runtime 알고리즘이나 SAM2 설정은 바꾸지 않았다.

## 현재 목표와 작업 범위

**목표는 SAM2까지 포함하여 현재 관측 1프레임을 약50ms에 처리하는 것이다.**
이는 약20Hz에 해당한다. 여기서는 이번에 측정한 vision→최종 Graph 경계를 기준으로 기록한다.
렌더링 제외/포함 수치를 함께 관리하고, 정책 추론·액션 실행까지의 제어주기와 구분한다.

현재 SAM2의 약430ms는 목표에 비해 크며 별도 원인 조사가 필요하다.
사용자는 이 문제를 인지했지만 **지금 SAM2를 수정하거나 해결하는 작업은 보류**했다.
당장의 후속 검토는 SAM2 외 처리시간을 더 줄이는 데 둔다.

로봇 필터·손목 gate는 전체 시간표에 포함한다. 해당 구현의 별도 담당 작업과 구분하고,
이 문서를 그 알고리즘에 대한 추가 변경으로 해석하지 않는다.
우선 검토할 구간은 Shape-First, packet/관측 구성, 점 기록·중복 제거,
엣지/Graph 구성, 이들을 잇는 동기화·복사·메타데이터 처리다.

## 전체 시간과 SAM2 외 약80ms의 해석

다음 전체 시간과77/83ms 근사치는 **최초 GPU 실측**의 기록을 보존한 것이다.
위 단계별 표의 추가 비교와 서로 다른 실행이며, 개선율 계산에 섞지 않는다.
필요한 커널이 준비된 동일 trace 재실행 결과다.

| 측정 경계 | 중앙값 | p95 | 의미 |
| --- | ---: | ---: | --- |
| 센서 준비 시작→Graph 완료 | 508.593ms | 513.115ms | 렌더링 제외, Terra 미호출 추적 프레임 |
| 렌더링 작업 + 센서→Graph 작업 | 514.073ms | 518.391ms | 같은 프레임의 두 작업 구간을 더한 값 |
| live의 연속 렌더 시작→Graph 반환 | 534.170ms | 538.557ms | 관측 생성 후 이전 프레임의 GT·video 기록 대기도 포함 |

대화에서 사용한 SAM2 외 시간은 다음 **근사치**다.

| 구분 | 계산 | 근사값 |
| --- | --- | ---: |
| 렌더링 제외 | 508.593 − 430.517 − 0.915 | 약77ms |
| 렌더링 포함 | 514.073 − 430.517 − 0.915 | 약83ms |

이 값들은 내부 동기화가 없는 전체 시간에서 단계별 진단 pass의 SAM2 중앙값을 뺀 것이다.
**SAM2 외 구간을 하나의 경계로 직접 측정한 값이나, 같은 프레임의 차이를 집계한 값은 아니다.**
현재 상태를 약80ms라고 표현하는 데 쓰며, 다음 변경의 정밀 비교에는
같은 입력·같은 timer 경계로 SAM2 외 구간을 직접 측정해야 한다.

추가 동일 입력 비교에서는 **mask·센서 준비 이후→Graph 반환**을 별도로 측정했다.
CPU 구버전 중앙값 **2539.591ms**, p95 **2632.705ms**;
현재 GPU 중앙값 **69.140ms**, p95 **73.597ms**였다.
이69ms는 렌더링·센서 준비·SAM2를 제외한 별도 mask-ready 재생이다.
기존77/83ms와 경계가 다르므로 코드 변경으로83→69ms 개선했다고 해석하지 않는다.
CPU full live 전체 시간은 각 단계 중앙값을 더해 만들어 넣지 않았다.

Graph 뒤의 model packing·정책 추론·command readback·물리 step·video/파일 저장은
위 센서→Graph timer 바깥이다. 50ms를 실제 제어주기 전체로 평가할 때는 그 비용도 확인해야 한다.

## 현재 SAM2 경로와 보류한 조사

주 live는 **VOS(Video Object Segmentation)의 `SAM2VideoPredictor` 경로**다.
`SAM2ImagePredictor`를 매 프레임 독립 실행하는 구조가 아니다.

Terra box를 초기 prompt로 넣고, 이후 `propagate_in_video`로 이전 상태·메모리를 유지하며
현재 프레임을 처리한다. 확인한 설정은 SAM2.1 Hiera Small, 내부 `image_size=1024`,
`num_maskmem=7`이다. **512는 센서·출력 mask 해상도이며 SAM2 내부 입력 크기와 다르다.**
현재는 두 카메라 각각 Peg·Box를 추적한다. 이후 Graph에서는 손목 Box를 제외한다.
측정한 약430.5ms에는 이 네 object track을 처리하는 현재 호출 경로가 포함된다.
서버에서는 `sam2._C` 누락으로 hole-filling 후처리를 건너뛰는 기존 환경 제약도 있었다.

사용자가 실시간 목표에 비해 SAM2 시간이 비정상적으로 크다고 보고 있다는 점을 남긴다.
다만 현재 자료만으로 특정 버그나 단일 원인을 확정하지 않는다.
추론 정밀도, 내부 해상도, object별 처리, memory attention, 호출 방식의 세부 시간은
나중에 별도로 검증할 조사 항목이다. **이번 추가 비교에서는 공통 SAM2 실행시간만 기록했고, SAM2 수정이나 원인별 분리 측정은 하지 않았다.**

## SAM2 외에서 추가 검토할 최적화 후보

다음은 기존 측정과 현재 코드에 근거한 **미구현·미검증 아이디어**다.
예상 절감량은 아직 없다. CUDA 실행 여부 외에 처리량·호출 수·동기화·할당을 줄이는 방향이다.

Shape-First에는 이미 ROI 외곽선 처리, voxel 대표점 커널, seed 거리 pruning,
큰 입력의 bucket별 FPS CUDA Graph 재생과 GPU provenance 처리가 있다.
이들을 새 제안으로 반복하지 않고 **현재 적용 이후 남은 비용**을 조사한다.

3mm dedup도 이미 cell 좌표로 거리 후보를 거르는 조건이 있지만,
현재 greedy 커널은 대표점을 선택할 때 입력 chunk를 순회한다.
인접 cell 목록을 쓰는 제안은 실제로 순회하는 후보 수를 줄일 수 있는지 검토하는 것이다.
greedy 커널이11.999ms 대부분이라고 아직 단정할 수는 없다.

packet·관측·Graph의 GPU 출력 경로는 이미 연결돼 있다.
다음 개선은 다시 GPU로 옮기는 작업보다 **GPU 경로 안의 반복 작업과 host 접점을 줄이는 작업**이다.
정확성 검사는 같은 의미를 유지한 채 계산·확인 횟수를 줄일 수 있는지 검토한다.

## 재컴파일은 평균 처리량과 별도로 관리할 문제

기존 실측의 첫 pass에서는 `_features` specialization이39회 발생했다.
1회 host 시간 중앙값은 **456.301ms**, p95는 **468.280ms**였다.
준비 프레임 이후 t9..38에도21회 발생했다.
따라서 시작할 때 한 번 warmup한 것만으로 모든 새 입력이 준비됐다고 볼 수 없다.

첫 pass의 센서→Graph p95는 **1,443.173ms**였고,
같은 trace의 점 수별 커널이 준비된 재실행에서는 **513.115ms**였다.
단계10의3.245ms는 준비된 커널의 실행 비용이다.
재컴파일 제거는 이3ms를 줄이는 문제와 구분하여, 큰 지연의 재발을 막는 과제로 기록한다.

## 50ms 목표에 필요한 시간 예산

현재 SAM2 외 약83ms는 SAM2를 제외해도50ms보다 길다.
SAM2 단축과 별개로 나머지 구간의 큰 폭 감소가 필요하다.
아래는 렌더링 포함 약83ms를 기준으로 한 **가정상의 예산 예시**이며 달성 예측이 아니다.

| 향후 SAM2 이미지 준비·추적에 드는 시간 가정 | 나머지 처리에 남는 예산 | 현재 약83ms에서 필요한 감소 |
| --- | ---: | ---: |
| 10ms | 40ms | 약43ms, 약52% |
| 20ms | 30ms | 약53ms, 약64% |
| 30ms | 20ms | 약63ms, 약76% |

SAM2가 빨라지면 지금 그 뒤에 숨는 CPU 준비가 critical path로 드러날 수 있다.
개별 단축량을 그대로 더해 전체50ms 달성을 예측하지 않고, 변경 후 전체 지연을 다시 측정한다.
중앙값과 p95를 함께 기록한다.

## 다음 작업을 재개할 때의 기준

1. 기존 실측 source와 현재 코드를 대조하여 이미 바뀐 구현이 있는지 확인한다.
2. 변경할 한 구간의 기존 시간을 같은 입력·같은 완료 경계로 먼저 측정한다.
3. 출력·선택 규칙을 보존하는 변경을 하나씩 적용한다.
4. GPU 완료 기준 전후 시간, 새 점 수의 compile/cache miss, 출력 일치를 함께 검증한다.
5. 마지막에는 SAM2 포함 전체 경계를 재측정한다. SAM2 조사는 별도 작업으로 재개한다.

최초 GPU 실측과 추가 비교는 단일 장면·고정 행동이며 Peg/Box 각각128점,259노드,80 directed edges였다.
최초 GPU 실측에서는 통과 surface edge가0이었지만 확인한 두 프레임의 free-space witness는774/678개로 비어 있지 않았다.
실제 visible-Peg 데이터와 surface 연결이 많은 장면에서도 확인해야 한다.
수치 근거는 Vast 실행이다. 최초 문서 정리는 기존 기록을 사용했고,
이번 CPU 비교 갱신에서는 같은 Vast 서버에서 새 입력 고정·CPU 재생·GPU 재측정을 수행했다.
macOS에서 CUDA를 새로 실행한 결과는 아니다.
