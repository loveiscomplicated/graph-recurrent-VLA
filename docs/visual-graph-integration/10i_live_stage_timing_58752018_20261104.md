# Task10-I 주 live 512 단계별 시간 측정 — 2026-11-04

주 live의 실제 `graph.plan_a_bc.rollout.run_episode`에서 사용자가 제시한
렌더링→Terra/SAM2→로봇 필터·손목 gate→최종 Graph 단계를 측정했다.
이번 변경은 실험용 계측 코드와 문서다. production 처리 로직·최적화·threshold는 바꾸지 않았다.
실행에는 변경 중인 작업트리의 고정 source snapshot을 사용했다.

**같은 관측 trace에 필요한 커널 준비가 끝난 경우**, 두512 카메라의
센서 준비→Graph 반환 중앙값은 **508.593ms**,
렌더링 작업까지 합친 처리시간은 **514.073ms**였다.
단계별 진단에서 SAM2 분할·추적은 **430.517ms**였다.
단, 새 점 수에 대한 Triton 컴파일이 추적 중에도 발생했다.
이 warmed trace 수치를 임의의 새 live 관측에도 항상 성립하는 지연시간으로 해석하면 안 된다.

## 실행 조건과 실제 범위

- RGB·Depth **512×512, base/hand 두 카메라**, 공통 좌표계 **EE**.

  `num_maskmem`은7이다. 512는 센서 입력·출력 mask의 해상도다.
- Terra `gpt-6.1-terra`, 기존 Standard/default tier·high effort·original detail 계약.
  본 측정의 실제 API 요청은 **2회**(각 카메라 t0), DINO 호출0회, 이후 trace 재실행의 정확한 RGB cache hit4회.
  앞선 계측 준비 실행까지 포함한 이번 작업의 실제 API 요청은 총4회였다.

  파일 로딩은 아래 추적 단계 표에서 제외했다.

## 시간 측정 방법

`natural`은 내부 단계에 새 CUDA 동기화를 넣지 않고 센서 준비 시작→Graph 작업 완료를 잰다.
실험 전용 빈 `TRITON_CACHE_DIR`에서 시작했으며 다른 실험의 기존 cache를 지우지 않았다.
GPU 완료는 최종 Graph 경계에서 기다린다.

`detailed`는 같은 trace를 다시 실행하면서 각 단계 앞/뒤에서 CUDA 완료를 기다린
CPU wall 시간이다. 커널 실행뿐 아니라 호출·할당·기존 검사·동기화를 포함한다.
중첩 함수는 exclusive 시간으로 배분하여 이중 합산하지 않았다.
CPU hull worker에는 CUDA 동기화를 넣지 않아 병행 준비를 유지했다.

`natural_warm`은 준비가 끝난 동일 trace를 내부 단계 동기화 없이 한 번 더 실행했다.
`detailed`와 `natural_warm`에서 새 Triton compile/cache-load 또는 FPS CUDA Graph 생성은0회였다.
각 pass의 t0 grounding cache 유무는 분리 기록했다.

Graph 동등성 검사에 필요한 CPU export는 Graph 종료 timer **뒤**에 실행했다.
video mask export·model packing·고정 policy·command readback·simulator physics·GT 평가·video encode·
Graph/trajectory 파일 저장은 센서→Graph 시간의 바깥이다.
렌더링 자체는 simulator 관측 생성에서 따로 측정했다.

## 전체 시간과 실제 주 live 경과시간

표 안의 숫자는 **중앙값 / p95 (ms)**다.

| pass | 조건 | 센서 준비→Graph 완료 | 렌더링 작업 + 센서→Graph 작업 |
| --- | --- | ---: | ---: |
| natural | 첫 실행: 빈 실험용 Triton cache | 511.713 / 1443.173 | 517.821 / 1449.494 |
| detailed | 같은 trace 재실행: 단계별 CUDA 완료 동기화 | 511.367 / 515.705 | 517.013 / 521.903 |

마지막 열은 **같은 현재 관측의 작업 구간을 프레임별로 더한 값**이며
연속된 하나의 stopwatch 구간은 아니다. 마지막 warm pass에서 렌더링/관측 출력 자체의
중앙값은5.321ms였다.

실제 live loop에서 렌더 시작 timestamp→해당 Graph 반환 timestamp의 연속 경과시간은
warm pass 중앙값 **534.170ms**, p95
**538.557ms**였다.
`env.step` 안에서 다음 관측을 렌더링한 뒤 이전 프레임의 GT·video 기록 등을 처리하므로,
이 수치에는 관측 생성 이후 다음 센서 처리에 들어갈 때까지의 bookkeeping 대기도 포함된다.

## 추적 중 발생한 Triton 재컴파일

초기화 t0의 센서→Graph 시간은 **23685.498ms**였다.
이 안에서 두 카메라의 RGB→grounding box scan 합계는 **7170.552ms**였다.
실제 `_request` 경계(인코딩·HTTP·응답 parse)의 카메라별 값은
**4822.197ms**, **2346.196ms**였다. 각 카메라1회 표본이므로 API p95를 추정하지 않는다.

첫 pass에서는 Triton specialization/cache-load 경로 진입이 **94회**,
관측된 host 시간 합계 **32901.033ms**였다.
이것은 전체 timer 안의 진단 subspan이며 전체에 다시 가산하는 값이 아니다.

| 커널 | specialization 횟수 | 관측 host 시간 합계(ms) | 1회 중앙값(ms) |
| --- | ---: | ---: | ---: |
| `_features` | 39 | 17807.746 | 456.301 |
| `_clip_compact` | 3 | 7685.803 | 3040.828 |
| `greedy` | 2 | 758.845 | 379.422 |
| `final_fps` | 2 | 612.371 | 306.186 |
| `fps_seed_bounded` | 1 | 611.718 | 611.718 |
| `fps_choose` | 9 | 531.638 | 58.606 |

특히 `fused_features_compact`는 현재 점 수 `n`을 `_features`의
**`N: tl.constexpr`** 인자로 전달한다. 마스크 유효 점 수가 변하면 새로운 specialization이 필요하다.
이번 `_features` specialization은 **39회**, 1회 중앙값
**456.301ms**, p95 **468.280ms**였다.
집계 구간 t9..38에도 이 커널의 specialization이
21회 발생했다.
새 점 수마다 처음 컴파일하는 비용이므로 단순히 최초1프레임만 제외해서 해결되는 비용이 아니다.

첫 pass의 t9..38에서 센서→Graph p95는
**1443.173ms**였다.
반면 같은 trace의 점 수별 커널이 이미 준비된 `natural_warm` p95는
**513.115ms**였다.
따라서 위 단계10의3ms대 값은 **준비된 specialization의 실행 지연**이다.
새로운 live 입력의 점 수에서도 이 값만 드는 것으로 일반화할 수 없다.

Shape-First FPS CUDA Graph 생성은 첫 pass t0에
**3회** 발생했고 이후 pass에서는0회였다.
생성 span 내부에 일부 Triton compilation이 중첩되므로 두 비용을 따로 더하지 않는다.
이번 작업에서는 이 재컴파일 문제를 최적화하지 않았다.

## 출력 일치·실행 검증

- `detailed` 대 첫 pass: **39/39프레임**의 다섯 Graph 배열 byte-level hash 일치.
- `natural_warm` 대 첫 pass: **39/39프레임** 일치. 최종 총78개 프레임 비교.
- 배열은 `node_input`, `node_type`, `edge_index`, `edge_attr`, `edge_type`이다.
- Graph와 TensorRecords가 CUDA이고 기본 `torch_cuda` backend인지 각 프레임 검사했다.
  주 live의 원래 packet·provenance·동시각/좌표계·point cap·Graph 유효성 검사도 실행했다.
- 이번 장면에서 매 프레임259노드, Peg128/Box128점,80 directed edges였다.
  저장된 Graph에서 robot–object48, Peg–Box32, 최종 통과 surface edge0을 확인했다.
  따라서 surface edge가 많이 통과하는 다른 장면의 전체시간을 대표하지 않는다.
- 최종 노드 배열로 surface 검사 prefix를 사후 CUDA 재실행하여 free-space 입력 크기를 확인했다.
  t0은774개, t25는678개 witness였다. 최종 surface edge가0이어도 free-space 입력이 빈 것은 아니었다.
  이는 입력 규모 확인용 검증으로 본 latency 표본에 섞지 않았다.
- 로컬 계측 unit test2개 통과. 실행 결과·source/archive hash 및 구간 합계 검증도 통과했다.
- CUDA 실행은 Vast 서버에서 했다. 현재 macOS host에서 CUDA를 실행한 결과는 아니다.
  이번 실험에서는 CPU perception/CPU graph, World 좌표계, 학습된 policy의 성공률은 측정하지 않았다.

## 환경 제약과 해석

설치 SAM2에서 `sam2._C` import 실패로 hole-filling 후처리를 건너뛴다는 경고가 있었다.
이 환경의 기존 동작으로 mask 추론·tracking은 완료됐다.
SAM2 후처리가 전부 활성화된 환경의 성능이나 출력과 같다고 주장하지 않는다.

이번 결과는 단일 reset seed와 고정 native-motion 행동에서 얻었다.
전체 visible-Peg 학습/평가 dataset의 latency 분포가 아니다.
원래 live logging/video 코드는 유지했지만 그 비용을 모두1..18의 처리시간에 넣지는 않았다.
관련 남은 비용은 [기존 주 live 잔여 비용 보고서](10i_live_nonrobot_coverage_audit_20261104.md#주-live에-남은-부가비용-구체화)를 함께 읽는다.
