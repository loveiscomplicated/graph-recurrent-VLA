# Task 10-I — sampling 정보 구성·Shape-First의 CUDA 전환

2026-11-03. 기존 GPU 역투영·`triton_fused` 특징 계산 뒤에 남아 있던 CPU
sampling 정보 구성과 Shape-First를 GPU 연산으로 전환하고 기본 Graph 경로에
연결했다. 수정 전 시간을 먼저 측정하고 source/입력/선택 결과를 보존한 뒤,
수정 후 동일 입력으로 출력 검증과 시간 비교를 수행했다.

## 측정 범위와 조건

- VastAI **58752018**, AMD EPYC 7543, RTX 3090.
- 기존 환경: Python 3.12.15, Torch 2.14.1+cu130, Triton 3.8.0,
  NumPy 2.5.4. 설치·driver·service 변경이나 다른 job 중지는 없었다.
- 저장된 실제 `10i_s1_0844_t080` hand-camera **512×512** 관측과 RGB 추론
  mask. Peg 61,056 pixels, Box 0 pixels. 앞선 역투영 검증과 같은 입력이다.
- **시작:** compact XYZ와 `triton_fused` 특징이 CUDA에 준비되고 동기화된 시점.
- **종료:** sampling 정보 구성·Shape-First 선택 완료, 결과가 CPU에서 사용 가능한 시점.
  기존 경로는 전체 점/특징을 내려받아 CPU에서 선택한다. 새 경로는 선택까지
  CUDA에서 처리하고 선택된 점/특징/provenance만 내려받는다.
- 파일 IO, RGB grounding/tracking, 로봇 필터, gate, 역투영, PCA/특징 계산,
  최종 EE packet 포장, 점 융합·최종 cap128/object·Graph 엣지 생성은 시간에서 제외한다.
  따라서 아래 수치는 전체 Graph 생성 시간이나 모델 latency가 아니다.
- warmup 20회, 본 측정 variant별 100회. CUDA 작업 완료를 기다리는 wall time이다.
  JIT/warmup과 출력 검증은 측정에서 제외한다. NumPy/BLAS 스레드 수는 1로
  제한했다. GPU kernel 시간만 보고하지 않고 Python 제어·allocation·동기화·
  device→host 반환도 포함했다. CPU affinity나 공유 host 부하는 고정하지 않았다.

## 결과

구현 변경 전에 수행한 baseline-only 실행:

| 경로 | 중앙값 | p95 |
| --- | ---: | ---: |
| 기존 GPU→CPU 정보 구성 + CPU Shape-First | **233.991ms** | **243.937ms** |

최종 구현에서 기존 경로와 새 경로를 같은 process에서 번갈아 실행한 paired 비교:

| 경로 | 중앙값 | p95 | 최소–최대 |
| --- | ---: | ---: | ---: |
| 기존 CPU 후처리 | **263.707ms** | **302.610ms** | 246.496–309.006ms |
| CUDA 정보 구성 + CUDA Shape-First + 선택 결과 CPU 반환 | **13.975ms** | **16.062ms** | 12.613–19.011ms |

이 최종 paired 표본에서 중앙값 기준 **18.87배**, 약 **94.7% 감소**다.
수정 전 최초 측정의 233.991ms와 비교하면 16.74배다. 그 사이의 첫 후보 paired
실행도 CPU 242.389ms / GPU 16.156ms를 기록했다. CPU 결과가 실행마다 변동했고
GPU도 14–16ms 수준으로 변동했으므로, 하나의 실제 입력에서 얻은 관측값을
모든 mask 크기·형태·두 카메라 입력에 대한 고정 배율로 해석하면 안 된다.

최종 실행의 별도 진단용 구간 분리 측정(20회 중앙값):

| 구간 | 기존 CPU 후처리 | CUDA 후처리 |
| --- | ---: | ---: |
| Sampling 정보 구성 | 71.044ms | 1.203ms |
| Shape-First + 필요한 CPU 반환 | 196.578ms | 14.284ms |

분리 측정은 중간 CUDA 동기화를 추가한 **별도 표본**이다. 이 중앙값들을 더해서
본 측정의 전체 중앙값을 복원할 수 없다. 원래 경로의 큰 비용 중에는 CPU에서
인접 pixel evidence를 구성하고, 1,008개 구조점으로 FPS 거리를 초기화하는
처리가 포함된다. 이 실험이 FPS 내부 구간을 독립 측정한 것은 아니므로,
196.578ms 전체를 FPS의 순수 비용으로 부르지는 않는다.

## 구현

`visual/runtime/cuda_sampling.py`와 `cuda_sampling_kernels.py`를 추가했다.

1. **정보 구성:** 기존 CUDA compact 특징에서 orientation/depth 후보와 경계
   원인을 생성한다. 기존 법선 변화·깊이 discontinuity 결과를 재사용하고,
   near/far depth 경계 원인은 CUDA에서 계산한다. CPU `pair_evidence`와
   dense CPU feature raster 재구성을 기본 경로에서 제거했다.
2. **외곽선:** GPU에서 foreground 8-connectivity / background 4-connectivity
   component를 구하고 padded exterior와 닿은 외부 contour만 선택한다.
   Moore walk, Jacob 종료 규칙, 양 방향·반복 최소 source를 고려한 canonical
   순서를 사용한다. 구멍 내부의 island는 제외한다. 관측 support로 걸러낸 뒤
   원래 순서를 유지하며 source를 중복 제거한다.
3. **Voxel 대표점:** 기존 median-depth 기반 nominal scale, floor voxel key,
   centroid에 가장 가까운 **원본 점**을 유지한다. FP64 연산을 사용하며 동점이면
   작은 source를 택하고 PCA/contour 입력 순서를 복원한다.
4. **Shape-First:** 기존 strict >20deg orientation, ratio .5/phase0,
   PCA 우선 + 새로운 silhouette source 순서, surface 추가 97/95를 유지한다.
5. **FPS:** 구조점 순서를 그대로 거리 초기값에 반영한다. GPU 병렬 거리 초기화와
   거리 갱신·최댓값 reduction을 사용하고 FP64, first-source 동점 규칙,
   선택 row 재사용 금지를 유지한다. 구조점이 없을 때의 첫 surface row는 0이다.
6. **반환:** 선택된 source/XYZ/특징과 provenance만 CPU로 전달한다. 새
   `vision_packet.complete_selected_vision_packet`가 원본 source/depth/K/mask를
   검증하고 기존 `complete_vision_packet`와 같은 EE 변환·v2 포장 코드를 재사용한다.

CUDA 함수는 모든 pixel/point 배열과 선택 결정을 GPU에 둔다. Python은 launch,
동적 cardinality와 component 수렴 여부의 scalar 값을 제어하므로 scalar host
동기화는 남아 있다. CUDA Graph 전체 capture나 완전한 CPU 무관 실행을
구현했다고 주장하지 않는다. 기존 contour/voxel helper의 사용되지 않는 분석용
중간 배열은 새 runtime 경로에서 만들지 않는다. 기존 NumPy 분석 API는 유지한다.

`CurrentGeometry`의 기존 `perception_backend='triton_fused'` 기본 경로가
이 CUDA sampling을 사용한다. `perception_backend='cpu'`는 과거 NumPy 진단
경로로 유지한다. `graph_perception.extract`/`to_cpu_evidence`도 비교·진단용으로
남아 있으나 기본 GPU packet 생성은 이 함수를 호출하지 않는다.

변경하지 않은 범위: 로봇 필터, gate, mask 생성 방식, 최종 점 융합·128점 제한,
Graph 엣지 정책, 학습/평가 데이터셋, 모델과 학습 설정. EE packet 이후의 Graph
조립은 여전히 CPU다. 새 GPU API는 현재 사용하는 Shape-First arm을 지원하며,
다른 과거 arm/ratio는 원래 NumPy API에서 사용한다.

### 최종 packet·Graph

기존 실데이터 검증 harness를 재사용하여 최신 최종 source에서 다시 실행했다.
원래 CPU dense packet/Graph 경로와 비교한 결과:

- 선택점, object ID, source provenance, feature validity 일치.
- 기존 dense `triton_fused` 대비 법선/depth jump/normal variation 최대 차이 0.
- 최종 Graph: 131 nodes, 1,006 directed edges.
- node/edge type, edge index/attr, source observation IDs는 exact.
- `node_input` 최대 절대 차이 `1.1920928955078125e-07`, `atol=2e-5` 통과.

이 Graph 검증은 실제 hand 관측과 **empty base support**를 사용했다. 두 경로에
같은 prepared mask/gate를 주입하고 로봇 필터/gate 실행을 우회했다. 원래 robot
FK·상태는 기존 asset으로 검증했다. 두 실제 카메라의 end-to-end rollout이나
policy 성공률 검증은 아니다. 합성 두 물체/두 카메라 Graph 계약은 별도로 통과했다.

### 계약 테스트

- Vast58752018 실제 CUDA: `test_cuda_sampling`, `test_graph_perception`,
  `test_pca_optimized` **24개 전부 pass, skip/failure 0**.
- 새 5개 계약은 51가지 mask contour case(빈 mask, image edge, 가는 구조,
  랜덤 연결, nested hole/island), voxel centroid와 source 동점, 중복 좌표
  FPS, 두 물체/빈 관측/무효 depth, 선택 metadata/provenance를 포함한다.
- 선택 전 `Tensor.cpu()`를 오류로 바꿔 GPU 선택 중 배열 다운로드가 없음을
  확인했다. 기본 packet 경로에서 CPU evidence/CPU prepare/CPU FPS 함수를
  오류로 바꿔도 출력 검증이 통과했다.
- 로컬 macOS `.venv`의 관련 기존/신규 묶음: **68개 중 61 pass, CUDA 7 skip**.
  로컬 CUDA는 실행하지 않았다. 이후 추가된 CUDA packet 계약까지 최종 원격
  24개에 포함해 실행했다. Simulator 생성·rollout은 실행하지 않았다.
- `git diff --check`와 변경 Python 파일의 syntax 검사를 통과했다.

첫 후보는 Triton contour scalar의 int32/int64 branch 타입 불일치로 계약
2개가 컴파일 실패했다. 타입을 일치시킨 뒤 모든 contour/FPS 계약이 통과했다.
실패 로그도 보존했다. 최종 선택점 불일치를 허용하거나 CPU fallback으로
검증을 통과시킨 것은 아니다.
