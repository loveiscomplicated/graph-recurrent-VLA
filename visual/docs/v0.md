# Vision prototype v0 (2026-10-08 ~ 10-09)

RGB-D → Grounding DINO → SAM2 → point cloud 파이프라인을 끝까지 돌려 본 첫 prototype이다. 3 episode 기준이라 결론 대부분은 v1(40 ep)에서 다시 확인했고, 그중 일부는 뒤집혔다(아래 마지막 절).

## 단계

| Step | 내용 | 상태 | 스크립트 |
|---|---|---|---|
| 1 | 환경 구축 (ManiSkill3, GDINO, SAM2, 체크포인트, smoke test) | 성공 (Vulkan은 EGL ICD로 우회) | `smoke_test.py` |
| 2 | RGB-D 수집 (3 ep, base + hand camera 512², GT seg/pose, 스크립트 삽입 정책 3/3 성공) | 성공 (mplib segfault → 자체 정책) | `collect.py` |
| 3 | Grounding (GDINO tiny, 프롬프트 16개 비교) | 성공 (init 프레임 6/6 IoU ≥ 0.96). 매 프레임 재검출은 불안정 | `grounding.py` |
| 4 | SAM2 tracking (frame 0 GDINO bbox 초기화, small / base+) | 부분 (ep001 peg가 44 프레임 완전 가림 후 재획득 실패) | `track_sam2.py` |
| 5 | point cloud (erosion → SOR → FPS ≤ 1024점) + 전체 파이프라인 | 성공 | `pointcloud.py`, `run_pipeline.py` |
| 6 | 속도·메모리 벤치마크 | 성공 | `run_pipeline.py` |
| 7 | tracker 비교 (SAM2.1, SAMURAI, EfficientTAM, 13개 설정) | 성공 | `track_compare.py`, `eval_step7.py` |
| 8 | re-anchor (confidence 하락 / 주기 → GDINO 재검출 → re-ID → SAM2 재프롬프트), 10개 설정 | 성공 | `reanchor.py` |

## 주요 수치 (RTX 3090, base_camera 512², 물체 2개, 3 ep, 워밍업 1 ep 제외)

| 항목 | 값 |

| grounding (GDINO tiny, query당) | 115 ms |
| tracking / frame (SAM2.1-small) | 46.4 ms (p95 47.1) |
| point cloud / frame (CPU) | 27.4 ms (p95 45.0) |
| FPS steady / online 추정 | 13.8 / 9.3 |
| GPU peak (tracking) | 3.46 GB |
| peg mask IoU (re-anchor 없음 → conf) | 0.726 → 0.901 |
| box mask IoU | 0.946 |
| point cloud centroid 오차 (GT mask cloud 대비) peg / box | 0.78 / 0.97 cm |

tracker 비교 (peg / box IoU, FPS): SAM2.1-small 0.726 / 0.946, 21.4 · +compile 0.916 / 0.947, 24.1 · SAMURAI-small 0.851 / 0.945, 13.0 · EfficientTAM-s 0.511 / 0.777, 23.2.

## v0에서 얻은 것
- GDINO는 "peg" 같은 이름보다 외형 묘사("red and white block", "cardboard box")가 잘 잡힌다. top-1을 그대로 쓰면 팔을 물체로 고르는 경우가 있다.
- 가장 큰 실패는 팔이 peg를 오래 가렸다가 다시 보일 때 SAM2가 peg를 다시 잡지 못하는 것이다.
- 주기적 re-anchor는 비용 대비 이득이 없고 SAM2 memory를 바꿔 오히려 결과를 뒤집을 수 있다. 소실 신호(confidence)로 트리거하는 편이 낫다.
- point cloud centroid는 "보이는 표면" 기준이라 GT pose와는 peg 7.6 cm / box 12 cm 차이가 난다. pose가 필요하면 형상 prior 맞춤이 필요하다.
- sim 20 Hz에 못 미친다. streaming 입력과 GPU point cloud가 필요하다.

## v1에서 뒤집힌 것
- compile on의 IoU 이득(0.73 → 0.92): 40 ep에서 +0.015 [−0.005, 0.050], 효과 없음.
- re-anchor conf의 이득(0.726 → 0.901): 40 ep에서 +0.011 [0.000, 0.034], 1 ep만 개선.
- SAMURAI 우위: 40 ep에서 +0.013 [−0.008, 0.050], 차이 없음.

세 차이 모두 3 ep 중 ep001(재등장 시 logit ≈ 0인 경계선 사례) 하나에서 나왔다. 그래서 v1부터는 40 ep 이상, dev/eval 분리, 신뢰구간으로만 비교한다.
